## Design Specificity Verdict

The strip is built from the app's own established "clickable client card" vocabulary (avatar + name + phone, `Link` to `/clientele/[id]`), not a generic pattern — good. But it invents a *fourth* variant of that vocabulary instead of reusing the one molecule already documented for this exact job (`PersonCard`, docstring: "used in... the cliente search results").

**Deterministic scan**: `detect.mjs --json app/page.tsx` → exit 0, `[]`. No mechanical findings. Browser visualization skipped — file under active concurrent edit by other sessions.

## What's Working

1. `clientMatches.length > 0 && (...)` makes the strip fully self-effacing on zero matches — matches this same screen's own doctrine for `AccueilGiftCards` ("s'efface quand il n'y a rien").
2. `ClientMatchCard`'s resting style has no permanent shadow (`border` only, shadow on hover) — actually *more* disciplined than the `ClientCard` it says it copies, and correctly avoids DESIGN.md's explicit "Don't: ship a rounded white card on an ambient shadow" rule.
3. Reuses `Legend` for the "Clientes" section title rather than inventing a heading — stays aligned with the one board-world token this unmigrated screen already uses.

## Priority Issues

**[P1] Tapping a client match strands the receptionist off Accueil with her filters lost.**
Why it matters: `query`/`period`/`persoStart` are local `useState` (page.tsx). The fiche's back link is hardcoded to `/clientele` (`fiche-cliente-view.tsx`), not Accueil — so the one scenario this feature exists for (she searched from Accueil because the client had no visible rdv) ends in a dead end back to Accueil's default "Aujourd'hui" view, search gone.
Fix: either open the client in an overlay/sheet (consistent with how RDV cards open `AppointmentDetailSheet` in place), or thread enough state (`?from=accueil` / `router.back()`) that the fiche can offer "Retour à l'Accueil" when that's genuinely where she came from.
Suggested command: `/impeccable shape` (this is an interaction-model decision, not a styling tweak).

**[P1] The only "this behaves differently" signal is `:hover`, which doesn't exist on a touchscreen tap.**
Why it matters: PRODUCT.md: "every primary interactive target must work as a tap, not rely on hover." At rest, `ClientMatchCard` (`border-base-300 bg-base-100 rounded-lg`) is nearly identical in weight to the RDV card directly beneath it — no persistent cue that this one navigates away entirely while that one opens an in-place sheet.
Fix: a persistent (non-hover) tell — a trailing "Fiche →" affordance, or a distinct fill (e.g. `bg-accent/30`).
Suggested command: `/impeccable polish`.

**[P2] Silent truncation at 4 matches, no count shown.**
`MAX_CLIENT_MATCHES = 4` drops the rest with zero indication more exist, and `searchClients` doesn't rank by relevance — array order. Répertoire's own search always states the true count (`Résultats · {filtered.length}`).
Fix: show the true count when truncated ("Clientes · 4 sur N"), and/or carry the query to `/clientele?q=` for a "voir tout" path.
Suggested command: `/impeccable clarify`.

**[P2] A third, divergent client-card style.**
`PersonCard` (52px avatar, `rounded-2xl`, flat, tier badge, already documented for "cliente search results"), `ClientCard` (40px avatar, `rounded-lg`, resting shadow, tier flag), and now `ClientMatchCard` (36px avatar, border-only, no tier) share no avatar size, elevation model, or metadata.
Fix: add a compact/`size="sm"` mode to `PersonCard` instead of a fourth ad hoc variant — one component to carry forward when Accueil migrates to the board world.
Suggested command: `/impeccable extract`.

**[P3] Avatar initial colour disagrees with its neighbour one scroll-length away.**
`AccueilDayList` payer avatar: `text-base-content font-bold`. `ClientMatchCard` avatar, directly above it: `text-secondary font-semibold`. Two rules for the same thing on the same screen.
Fix: match the local `AccueilDayList` convention.
Suggested command: `/impeccable polish`.

## Minor Observations

- Card height (avatar 36px + padding + 2 text lines ≈ 60px) coincidentally lands on DESIGN.md's `tap-target-ideal`, but isn't CSS-enforced — a longer name could shrink it. Consider `min-h-[60px]` explicitly.
- `grid-cols-2 sm:grid-cols-4` (Clientes) stacked directly above `grid-cols-3` (RDV) reads as an accidental seam, not an intentional density shift.
